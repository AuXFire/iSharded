# iSharded results

This is the full record of what has been measured and checked about iSharded: speed, behaviour under failure, whether replies stay the same, security probes, and the automated tests. Each result says what it ran on, so a figure from two CPU stages on one laptop is never read as a figure from rented GPUs in two countries. The last sections list what has not been measured yet, and how to add a result here.

[The guide](GUIDE.md) explains how each feature works and links back to the results that matter for it. Where the guide already explains a result in depth, the row here links to that section instead of repeating it.

## How to read this

Each row gives what was tested, the setup, the numbers exactly as the source states them, the date, the source, and its kind:

- Measured: real code was timed or counted on real machines, on the network stated. Where delay was added to the links by Linux `tc netem` or a delay relay, the kind says "emulated" and gives the delay.
- Estimated: worked out from measured parts, such as a planner's figure or a sum of measured stage times. Nothing ran end to end.
- Simulated: stand-in stages, stand-in tools or sleeps took the place of model stages, usually on an emulated network with the delay stated, or a replay of recorded data drove the timing.

A row can hold a measured part and an estimated part, and then it says which is which. Where two sources disagree, both figures are given.

Replies identical means token for token: the same text, compared against a run with the feature off, an unbroken run, or one stage holding the whole model, as each row says.

Sources are a section of these docs, a commit on `main`, or a lane report. A lane is one piece of work on its own branch: a builder made the change and measured it, and a separate verifier checked it and reran what it could. Lanes ran in five rounds between 2026-11-06 and 2026-11-07, and their reports are not kept in the repository. A commit is named only where it is on `main`. Dates are when the result was measured, or, for rows from the first commit of the repository on 2026-11-05, when it was first written down. "Pre-fix" marks a result that found a bug, with the fix named where a source names it.

Some rows use short names from the lanes. In draft rows, L is how many tokens the draft guesses in one pass and A is how many are accepted on average. R is the time of one trip around the route, g the draft's time for one guess, and N the number of replies sent at once. In planner rows, "the law" is the guide's formula for a route's speed, in [What a route costs](GUIDE.md#what-a-route-costs), where L means tokens made per wrong guess.

Hardware is described the way the guide does. The test pool is an RX 7900 XT desktop and an RTX 3060 laptop, both on Wi-Fi with a 15 ms ping. The desktop has a Ryzen 5800X3D. "The laptop" alone means that RTX 3060 laptop, often with other work running, which the rows say. Linux on the laptop means WSL Ubuntu.

## Not measured yet

Scale and hardware:

- Nothing past seven machines. Seven ran for about two hours; larger meshes are design.
- macOS has not run a real model, only CI. The aarch64 wheel has never loaded on Arm. `iSharded-Setup.exe` has never been run, and a successful service install has not been run.
- FP32 split independence only on CPU stages on one machine with no draft; GPUs and mixed hardware are unchecked.
- Embeddings on a GPU or outside Windows. Vision on a GPU, across a real network, or outside Windows.
- Llama, Mistral and Hermes tool calls have never run on a mesh. No model larger than the 27B tried for tool calling.
- The chat page has been used only in Chrome.
- `isharded bench` has no GPU numbers and no full default run (prompts of 128 and 3400, `--parallel 1,4,8`, 200 tokens).
- One load failure at `--parallel 2` on the test pool was transient, and its cause was never found.

Failures:

- Leaks over days: soaks total under two hours, and the longest continuous one ran under an hour.
- A node blip under 30 s and recovery of a quarantined node, on real hardware. A live node failing to load: simulated failures only.
- One-row resume has not run on a real mesh, with a draft, or beside other replies, and not again on the 235B mesh. Resume speed on a slow route is unmeasured. Kill tests did not cover merged passes.
- A mid-reply kill with the ring on after the draft repair, and a hybrid model through a mid-reply kill.
- A wedged, not dead, stage process with the draft in its process.
- A hung Python-path call on a live process: 30 s plus 1 s a row, and a replay over about 8 rows would exceed 40 s. Not measured on a real ring.
- The 10 s pulse limit under heavy paging, a cold first pass on a slow disk, a late pass after a replay clears.
- A truly dead hop (new connections also silent) cannot meet 5 s plus twice the round trip (9.38 s measured once, not rerun). The ring's 10 s floor on answers may raise false alarms on slow healthy stages, and a direct closing link silent in one direction is not caught (a 62 s wait on two stages): both reasoned, not measured. A 60 s stop where the ring never looked whole is unexplained.
- Ring tests hang under CPU load on old and new code; the cause was never found.
- Text kept across a live route change, for a prompt whose text depends on the split: GPU run 1's replies that crossed a join, cordon or leave used prompts that give the same text on every split. Why the status call stayed at about 1.5 s after a node left was not found.
- Native links have not carried a real model over the Python ring path since the links fixes.
- A hop redial with a round trip over about 600 ms may fail its 2 s handshake deadline. A flood from many addresses can still fill 64 places.

Speed:

- The live mesh's hop cost of about 10 ms against 2.1 ms on the desktop: the 3-5x gap was never reproduced or explained. Linux hop costs for the Python path were not measured.
- Why the live seven-node chain skipped the Linux slow-start doubling was never checked on a cloud node.
- The 5 to 8 s first tokens on new prompts on the seven-node mesh stayed unexplained. The RAM spill theory was wrong, and the emulated explanation was never confirmed with a 1 s against 7 s idle test on the mesh.
- All seven-site and five-node figures from the design, stress and plan lanes are estimates or simulations. Moving 80-86 GiB for about 94 ms a token is an estimate.
- Route order from measured links has never run on a real mesh. A netem test of the planner's proposals, and a kill mid-cutover, were not run; no apply path exists. The planner's law was not checked on a real draft pipeline, and its speed effect on real routes is unmeasured. Its 10% allowance for less spill is a judgment.
- Heartbeat tables and the 1,220 to 454 ms come from stand-in tools on netem, not real engine stages. 1 MiB padding on links under about 1.7 Mbit/s may trip the 5 s ack timeout (reasoned). No WAN time saving from kept connections was measured. The 64-row warm gain rests on three loads per arm with differing routes.
- No Qwen3-235B and 0.6B draft pair existed locally, so acceptance figures come from proxy pairs; the real 0.6B accepted length on the mesh is unknown. A stronger draft such as Qwen3-8B has not run on the 235B, and no draft ladder of 0.6B, 4B and 8B was run. No honest draft against lookup comparison: only a copy of the model as draft. EAGLE-3, multi-token drafts and DFlash, QUIC, and T=1.0 are unmeasured.
- Draft timing alone on an A40 (the 8.5-11 ms mesh figure) was not re-measured, and the draft-apart comparison never ran on a real mesh.
- Tree checks only on Qwen3-0.6B; GPU bit-exactness of hedge rows is untested. Long-context cost of kv_unified is unmeasured. The row cost curve from 1 to 64 rows on a real 235B stage has only the 4-row point (3.4x).
- No whole pipelined reply on GPU stages for recurrent models: GPU run 1 ran only the default load's 24-token probes there, at 14.2 to 14.7 tokens/s against 27.1 to 27.8 plain. The loss of a guessed way on GPU stages is unmeasured. The Qwen3.6-27B slots table predates the recurrent change.
- Auto slots on a large model, with kv_unified, and with a draft sweep on real stages. The merged-pass gain without a draft was not shown base against branch. `--parallel 8` with a draft against planned VRAM was not checked on a GPU.
- The bias in choosing the draft (round five) is neither fixed nor disproved. A merged-step retry was not tested on hybrid Qwen3.5.
- Real row transfer time on a slow link; the sized link probe and the status page's new link fields were tested only with mock transports.
- Most speed-lane benchmark figures were not rerun by the verifier, and neither were the recurrent snapshot costs.
- GPU run 1's ceiling is `llama-bench`, with no server, HTTP or sampling; stock `llama-server` on one A40 was not measured. At 4 stages only plain decoding ran: no default load, chat settings, links, many at once or failures. No even 3-stage split was measured on the 4-stage pods, as no load option forces a split.
- The default load's pipelined probes cost about 6 ms a token on single-GPU pods at 2 and 3 stages while it chooses plain anyway; whether a draft ever wins there was not measured, and the draft's changing text at temperature 0 on 1 stage was not rerun.
- Mixed versions: an old engine without the keep flag, a null `draft_tokens`, and protocol version bumps (6 to 7, 7 to 8) were not exercised.

Security and features:

- No human security review or penetration test; three AI reviews only.
- Checking answers measured only with every route on one machine. A network nobody owns has run only as three nodes on one machine, not between strangers.

## Adding results

A result goes here when it is measured, with enough setup that someone else could run it again.

1. Run it the way the row will describe. For speed on a running mesh, use `isharded bench`, described in [isharded bench](GUIDE.md#isharded-bench). Its `--markdown` report names the model, quantization, slots, stages, GPUs, precision, countries, link times and commits, and leaves out addresses, keys, machine names and paths, so it can be pasted. Use `--compare before.json after.json` to set two runs side by side.
2. Add a row to the section it belongs in, with what was tested, the setup, the numbers exactly as measured, the date, and Measured, Estimated or Simulated. For an emulated network, give the delay and the tool.
3. Name the commit if it is on `main`; otherwise give the date alone. Name the doc section if the guide explains it.
4. Keep every figure. Do not round, merge or improve a number. When a rerun disagrees, add its figures beside the first ones. A range from repeated runs keeps both ends.
5. Say what the result does not cover, and add it to [Not measured yet](#not-measured-yet) if it leaves a gap. Remove a line there only when a row here closes it.
6. Leave out drive letters, local paths, user and machine names, addresses, hostnames, and key names. Countries are fine where an operator shows one.
